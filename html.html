Validaciones, UX y errores controlados — Agenda ADSO v6

La Agenda ADSO ya funciona: guarda, lista y elimina contactos. Hoy la hacemos profesional: validamos lo que escribe el usuario, le explicamos con claridad qué salió mal, y controlamos qué pasa mientras se guarda un dato.

Propósito y resultados de aprendizaje

Agregamos validaciones al formulario de contactos, mostramos mensajes de error claros, controlamos el estado de envío del formulario, y perfeccionamos los mensajes de error que vienen de la API (JSON Server).

Resultados de aprendizaje relacionados

01

El problema de UX en el formulario actual

Aunque el formulario de la v5 permite crear contactos, hoy tiene varios huecos silenciosos:

  • No muestra mensajes claros cuando faltan datos.
  • No valida el formato mínimo del correo.
  • Permite hacer clic varias veces en el botón mientras guarda.
  • Los errores de la API son poco amigables (o inexistentes para el usuario).
"¿Qué siente un usuario cuando llena un formulario y no sabe qué hizo mal?"

Esa pregunta es el punto de partida de todo lo que viene: validaciones y UX no son un lujo estético, son comunicación con la persona que usa la app.

02

Un estado de errores por campo

Además del estado form (los valores), y del nuevo errores (los mensajes), agregamos enviando para controlar el botón mientras se guarda.

src/components/FormularioContacto.jsx
import { useState } from "react";

function FormularioContacto({ onAgregar }) {
  // Valores de cada campo
  const [form, setForm] = useState({
    nombre: "", telefono: "", correo: "", etiqueta: "",
  });

  // Mensajes de error, uno por campo obligatorio
  const [errores, setErrores] = useState({
    nombre: "", telefono: "", correo: "",
  });

  // true mientras se está guardando en la API
  const [enviando, setEnviando] = useState(false);
errores: { nombre, telefono, correo }
Un objeto de estado paralelo a form: por cada campo obligatorio, guarda el mensaje de error (o un string vacío si está bien).
enviando
Un booleano que responde a una sola pregunta: "¿ya hice clic en Agregar y sigo esperando la respuesta del servidor?" Con eso desactivamos el botón y cambiamos su texto.
03

validarFormulario() con .trim()

Antes de guardar, revisamos los tres campos obligatorios. .trim() quita espacios al inicio/final, para que " " no cuente como un nombre válido.

validarFormulario()
function validarFormulario() {
  const nuevosErrores = { nombre: "", telefono: "", correo: "" };

  if (!form.nombre.trim()) {
    nuevosErrores.nombre = "El nombre es obligatorio.";
  }
  if (!form.telefono.trim()) {
    nuevosErrores.telefono = "El teléfono es obligatorio.";
  }
  if (!form.correo.trim()) {
    nuevosErrores.correo = "El correo es obligatorio.";
  } else if (!form.correo.includes("@")) {
    nuevosErrores.correo = "El correo debe contener @.";
  }

  setErrores(nuevosErrores);

  return (
    !nuevosErrores.nombre &&
    !nuevosErrores.telefono &&
    !nuevosErrores.correo
  );
}
!form.nombre.trim()
Si después de quitar espacios el string queda vacío, es "falsy" — entra al if y se asigna el mensaje de error.
correo: dos validaciones en cascada
Primero se revisa que no esté vacío; solo si pasó esa, se revisa que contenga "@". Son mensajes distintos para problemas distintos.
return (!a && !b && !c)
La función es válida (devuelve true) solo si los tres mensajes de error quedaron vacíos — ni uno solo campo puede fallar.

05

El estado "enviando" controla el botón

Mientras se espera la respuesta del servidor, el botón se desactiva y cambia su texto — así evitamos que un doble clic cree el contacto dos veces.

onSubmit + botón
const onSubmit = async (e) => {
  e.preventDefault();
  const esValido = validarFormulario();
  if (!esValido) return;

  try {
    setEnviando(true);
    await onAgregar(form); // puede tardar (llamada a la API)
    setForm({ nombre:"", telefono:"", correo:"", etiqueta:"" });
    setErrores({ nombre:"", telefono:"", correo:"" });
  } finally {
    setEnviando(false); // pase lo que pase, reactivamos el botón
  }
};

// En el JSX:
<button type="submit" disabled={enviando}>
  {enviando ? "Guardando..." : "Agregar contacto"}
</button>
try / finally
El finally se ejecuta siempre, haya éxito o error — así el botón nunca queda "trabado" en estado deshabilitado si algo falla.
disabled={'{enviando}'}
Mientras enviando es true, el botón no responde a más clics.
{'{enviando ? "Guardando..." : "Agregar contacto"}'}
El texto del botón le confirma al usuario que su clic sí funcionó y algo está pasando — reduce la ansiedad de "¿le di clic o no?".
06

Mensajes de error de API, más amigables (App.jsx)

Cuando algo falla — el servidor está apagado, por ejemplo — no mostramos el error técnico: mostramos un mensaje humano, en un banner visible.

App.jsx — carga y creación con manejo de error
const [error, setError] = useState("");

useEffect(() => {
  const cargarContactos = async () => {
    try {
      setCargando(true);
      setError("");
      const data = await listarContactos();
      setContactos(data);
    } catch (error) {
      console.error("Error al cargar contactos:", error);
      setError(
        "No se pudieron cargar los contactos. Verifica que el
        servidor esté encendido e intenta de nuevo."
      );
    } finally {
      setCargando(false);
    }
  };
  cargarContactos();
}, []);
console.error(...) vs setError(...)
El detalle técnico se queda en la consola, para depurar. El usuario recibe una frase clara, sin jerga, sobre qué hacer.
setError("") al inicio del try
Antes de reintentar, limpiamos cualquier error anterior — así un segundo intento exitoso no deja un mensaje de error "fantasma" en pantalla.
Banner de error global en el JSX
{error && (
  <div className="bg-red-50 border border-red-200 rounded-xl px-4 py-3">
    <p className="text-sm font-medium text-red-700">{error}</p>
  </div>
)}
